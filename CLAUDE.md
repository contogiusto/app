## Progetto
Webapp per ordini e pagamenti nei ristoranti (ruoli: ristoratore, cameriere, cliente via QR). Monorepo:
- `frontend/` — React + TypeScript + Vite (test: Vitest, lint: oxlint)
- `backend/` — FastAPI + SQLAlchemy 2 + Alembic (Python ≥3.11, gestito con `uv`; è anche il servizio Vercel `api`)

## Processo (SDLC)
Per ogni funzionalità non banale: **intent → design → build → verify → review → ship** (dettagli in [docs/sdlc.md](docs/sdlc.md)). I documenti stanno nel repo: `docs/intents/NNNN-*.md` (problema e criteri di successo), `docs/design/NNNN-*.md` (approccio e piano a task, stesso numero), `docs/adr/` (decisioni durature). Comandi: `/intent`, `/design`, `/new-feature`, `/ship`. Non iniziare a scrivere codice per un intent senza design approvato; i cambi piccoli (una frase di diff) saltano intent e design. Prima di dire "fatto" verifica i criteri di successo dell'intent con evidenza.

## Comandi
```bash
docker compose up -d postgres                        # DB locale
cd backend && uv sync && uv run uvicorn app.main:app --reload   # API su :8000
cd frontend && npm ci && npm run dev                 # UI su :5173 (proxy /api → :8000)
# Più copie del progetto in parallelo (altre porte): API_PROXY=http://localhost:8001 npm run dev -- --port 5174

# Controlli (gli stessi della CI; i test usano il Postgres di docker compose su :5433)
cd backend && uv run ruff check . && uv run ruff format --check . && uv run pytest
cd frontend && npm run lint && npm run test && npm run build

# Migration (da backend/)
uv run alembic revision --autogenerate -m "descrizione"
uv run alembic upgrade head

# Dopo ogni modifica a endpoint o schemi dell'API: aggiorna OpenAPI e tipi del frontend
cd backend && uv run python -m app.export_openapi && cd ../frontend && npm run api:types
```

## Frontend
- Tipi dell'API **generati**: `frontend/src/api/schema.d.ts` deriva da `backend/openapi.json`; non si modificano a mano. Il test `test_openapi_sync` (backend) e un passo della CI (frontend) falliscono se sono in ritardo. Il generatore gira con `npx` a versione fissa perché `openapi-typescript` non supporta ancora TypeScript 7.
- Tutte le chiamate passano da `src/api/client.ts` (`api.*`, errori come `ApiError` con messaggio pronto per l'utente). Gli importi arrivano come stringhe ("8.50") e si usano in centesimi interi con `src/lib/money.ts`.
- Il tema è in `src/styles/theme.css` e **solo lì** si definiscono colori, font e raggi: nei componenti si usano i token (`--surface`, `--text-2`, `--accent`, `--danger-*`…, mai hex). Le scelte e le regole d'uso sono in `DESIGN.md`; i componenti base in `src/ui/`. Titoli con la classe `.display`, importi con `.tnum`. Font self-hosted (`@fontsource-variable/geist`), niente Google Fonts.
- Il token del QR resta fuori dall'URL delle chiamate: va nell'header `X-Table-Token` (già gestito dal client).
- Percorso cliente (`/table/:id?token=…`) in `src/customer/`: `CustomerApp` (dati, polling ogni 3 s, passi), `screens.tsx` (schermate), `logic.ts` (funzioni pure), `storage.ts` (cosa ricorda il browser). Il server decide quote e chiusura (`next_share`, sessione assente = conto chiuso): il frontend li mostra soltanto, non li ricalcola.
- Scelte di prodotto per il pagamento: nessun form carta (i pagamenti sono simulati e non si devono far digitare numeri di carta in un form finto: con un provider reale i campi li ospita il provider); l'elenco dei commensali mostra solo chi ha già pagato (il backend non registra chi "entra" al tavolo); l'identità del cliente vale per una sola sessione.
- Auth dello staff (`src/staff/`): `/staff/login` (pubblica, `LoginScreen.tsx`) chiama `api.login`. `AuthProvider.tsx` (montato in `App.tsx`) tiene `{token, role, username}` e lo salva in `localStorage` (`session.ts`, come `customer/storage.ts`); `useAuth()` (`auth.ts`) dà `session`, `login`, `logout`, `notice`. Il `exp` del JWT si legge senza verificare la firma: un token scaduto non si riprende dallo storage e, a pagina aperta, un timer riporta al login con "Sessione scaduta". `RequireRole` protegge le rotte: anonimo → `/staff/login` col ritorno alla pagina richiesta; `/waiter/*` per WAITER e ADMIN; `/admin/*` solo ADMIN (un WAITER viene mandato a `/waiter`). Dopo il login WAITER → `/waiter`, ADMIN → `/admin`.
- Chiamate staff: `api.staff.{tables,sessions,orders,payments,menu}` in `src/api/client.ts` aggiungono da sole il token Bearer; su 401 (o token mancante/scaduto) fanno il logout e rilanciano `ApiError`, quindi le schermate non devono gestirlo. Non servono al login (`api.login` fa eccezione: il suo 401 è "Credenziali non valide"). Il QR (`api.staff.tables.qr`, solo ADMIN) richiede l'header Authorization, che un `<img src>` non manda: usa l'hook `useQrUrl(tableId)` (scarica il blob e dà un URL locale; dopo `regenerateQr` invalida `['qr', id]`). Il login non restituisce il nome del locale: le schermate staff non lo mostrano.
- Dove si lavora: le schermate del cameriere vanno in `src/waiter/` (entry `WaiterApp.tsx`, default export, con sotto-rotte relative in un proprio `<Routes>`) e quelle del ristoratore in `src/admin/` (entry `AdminApp.tsx`). Usano `StaffLayout` (`title`, `actions`, `children`: barra con utente, ruolo ed "Esci") e **non** modificano `App.tsx`, `src/staff/` né `client.ts` salvo necessità concordata. Nei test di schermata basta `vi.mock` di `api.staff` come in `customer/CustomerApp.test.tsx`; per simulare un login `staff/testing.ts` offre `fakeJwt()`.
- Cameriere (`src/waiter/`): `WaiterApp.tsx` ha una sola rotta (`/waiter` = sala, `/waiter/table/:id` = tavolo) che monta `Floor.tsx` (elenco tavoli a sinistra, tavolo scelto a destra; su schermi stretti si vede una cosa per volta). Un tavolo libero mostra `OpenSessionPane` (coperti 1-100); uno occupato `SessionPanel` (comanda, conto, pagamenti con conferma dei contanti), con `MenuPicker` (scheda del menu pubblico per categoria, con quantità) e `CloseDialog` (chiusura forzata con conferma). `queries.ts` ha le query con polling ogni 3 s (tavoli, `GET /api/sessions/open` per coperti/pagato/contanti da confermare di tutti i tavoli in una richiesta, e i tre elenchi della sessione); dopo ogni scrittura si invalida `['waiter']`. Una sessione che si chiude mentre la si guarda resta visibile in sola lettura ("Torna al tavolo"). `parts.tsx` ha `ErrorNote` e `Overlay` (modale con Esc, focus e Tab gestiti), `logic.ts` le funzioni pure. Ordini e rimozioni si disabilitano da soli appena esiste un pagamento (stessa regola del server, che risponde comunque 409).
- Ristoratore (`src/admin/`): `AdminApp.tsx` (default export, dentro `StaffLayout` titolo "Gestione") ha la navigazione e le sotto-rotte `/admin/menu` (`MenuScreen.tsx`: menu completo per categoria, piatto nuovo/modifica/elimina, interruttore di disponibilità) e `/admin/tables` (`TablesScreen.tsx`: elenco tavoli, nuovo tavolo, QR con `useQrUrl`, stampa, rigenera); `/admin` e le rotte ignote vanno a `menu`. `price.ts` valida il prezzo digitato in centesimi (max 999999,99) e lo manda all'API come stringa decimale; `Modal.tsx` è la finestra modale accessibile (Esc, focus, `alertdialog` per le conferme); `parts.tsx` ha `SectionHeader`, `Toggle` (`role="switch"`) ed `ErrorNote`; `icons.tsx` le icone usate solo qui. Eliminare un piatto già ordinato dà 409: la finestra offre "Rendi non disponibile". Il foglio da stampare (`.print-sheet`, in `admin.css`) viene montato nel `body` solo durante `window.print()` e in stampa è l'unica cosa visibile: il QR non va mai salvato come file nel repo (contiene il token del tavolo).
- Account del cliente (`src/account/`, parallelo all'auth dello staff: stesso schema, chiavi e contesti separati): `AccountProvider` (montato in `App.tsx`) tiene `{token, customer}` in `localStorage` (`cg:account`, `session.ts`) e dà `useAccount()` → `session` (null = ospite), `login`, `register`, `logout`, `setCustomer`, `notice`. Un token scaduto non si riprende e, a pagina aperta, un timer fa uscire con "Sessione scaduta". `api.customer.{register,login,me,update,remove,payments}` in `client.ts` (le ultime quattro aggiungono il token e su 401 fanno il logout). **Pagare al tavolo non richiede il login**: `api.table.pay` aggiunge da solo il token cliente se c'è ed è valido, altrimenti si paga da ospite (il server lega il pagamento all'account solo se il token è valido).
- Rotte del cliente (definite in `App.tsx`/`AccountArea.tsx`, un file per pagina): `/` = `account/HomePage` (accesso e registrazione, link all'accesso staff), `/privacy` = `account/PrivacyPage`, `/customer/*` protetta da `RequireCustomer` → `AccountArea` con `home`, `history`, `profile` (in `src/account/`) e `scan` (`src/scanner/ScanPage`). Il ritorno dopo il login passa da `?redirect=` e **va sempre letto con `safeRedirect`** (`account/redirect.ts`: accetta solo percorsi interni, contro l'open redirect); `loginUrl(to, 'login' | 'register')` costruisce il link. `?mode=register` apre la home sulla registrazione.
- Account al tavolo e scanner QR: aprendo `/table/:id?token=…` senza account compare `EntryChoice` (Accedi / Registrati / Continua come ospite; testo su ospite e storico). Accedi e Registrati vanno a `loginUrl(/table/<id>?token=<token>, …)` (sempre il percorso completo, token compreso, anche se l'URL attuale non lo aveva); "ospite" si ricorda per la **sessione** del tavolo (`storage.ts`: `loadGuest`/`saveGuest`, mai per sempre). Chi è collegato (`useAccount().session`) salta scelta e nome: il nome al tavolo è `first_name last_name` (salvato come identità con `account: true`, che vale solo finché l'account è collegato), si vede "Stai pagando come …" con "Non sei tu? Esci" (logout + torna alla scelta, il tavolo resta). Dopo il pagamento: collegato → "Il pagamento è nel tuo storico"; ospite → invito `loginUrl('/customer/home','register')`. Scanner (`src/scanner/ScanPage.tsx`, `/customer/scan`): `BarcodeDetector` o, in fallback, `jsqr` (Apache-2.0, versione fissa, caricato a richiesta) su canvas; la fotocamera si spegne allo smontaggio, dopo la lettura e con la scheda in background; c'è sempre il campo "Incolla il link del tavolo". **Il contenuto del QR è dato non fidato: si valida solo con `parseTableLink` (`scanner/parseTableLink.ts`: stessa origine, percorso esatto `/table/<cifre>`, `token` non vuoto, percorso ricostruito dai pezzi) e si naviga con il router; mai `window.location` verso il testo letto.**
- Pagine dell'account (`src/account/`): `HomePage` (`/`: schede Accedi/Registrati, legge `?redirect=` con `safeRedirect` e `?mode=register`, validazione lato client senza i messaggi nativi del browser, `notice` di `useAccount`), `PrivacyPage` (informativa; i dati del titolare stanno in `privacyConfig.ts` e restano "da indicare" finché vuoti: l'informativa va fatta rivedere dal titolare), `AccountLayout` (barra in alto, navigazione in basso su telefono) con `AccountHome`, `HistoryPage` e `ProfilePage` (dati, uscita, eliminazione con conferma `alertdialog` e password; usa `admin/Modal`). `payments.tsx` ha `PaymentCard`/`StatusChip` (con OWN i piatti sono quelli pagati, con ROMANA quelli del tavolo), `queries.ts` il `usePayments` (chiave con l'id cliente), `account.css` focus e responsive. Nei test: `testing.tsx` (`renderApp`, `loginAsAnna`) e `where.tsx` (nei `vi.mock` non importare `testing.tsx`: importa `App` e crea un ciclo che blocca Vitest).
- Nei test, `src/test/setup.ts` smonta i componenti a fine test: non rimuoverlo o i test si influenzano a vicenda.

## Regole
- Mai committare su `main` né pushare su `main`: si lavora su `feat/*`, `fix/*`, `chore/*` e si apre una PR.
- Test-first per la logica applicativa; ogni cambio di schema DB ha la sua migration Alembic (compatibile con la versione di codice precedente: vedi ADR 0002).
- Dopo `alembic revision --autogenerate` controlla il file: Alembic duplica i CHECK degli `Enum` (vedi la migration iniziale) e va rivisto a mano.
- Tutte le route API vivono sotto `/api` (richiesto dal routing Vercel).
- Niente WebSocket (serverless): il real-time è polling dal frontend. Vedi ADR 0001.
- Segreti solo da variabili d'ambiente (`.env.example` elenca quelle richieste); mai nel codice.
- Auth staff: JWT HS256 (24h) da `POST /api/auth/login`. Le route protette usano le dipendenze di `app/deps.py` (`CurrentUser`, `AdminUser`, `require_roles(...)`); lettura menu pubblica, scrittura solo ADMIN.
- `JWT_SECRET` va impostato su Vercel (Production e Preview, almeno 32 caratteri casuali): in produzione col valore di default login e token rispondono con errore.
- Utenti staff: nessuna password predefinita. **Dopo il primo deploy della fase 3a**: `promote-superadmin <admin attuale>` e poi `create-user <nome> ADMIN --restaurant <slug>` per l'admin del locale (la migration lega gli utenti esistenti al primo ristorante e gli assegna uno slug). Si creano con `cd backend && uv run python -m app.cli create-user <username> <ADMIN|WAITER>` (con `DATABASE_URL` del DB di destinazione). Comandi della CLI: `create-restaurant <slug> <nome>`, `create-user <username> <SUPERADMIN|ADMIN|WAITER> [--restaurant <slug>]` (ADMIN e WAITER richiedono il ristorante), `promote-superadmin <username> [--restaurant <slug>]`, `list-users` (id, username, ruolo, ristorante; mai gli hash) e `reset-password <username> [--restaurant <slug>]` (le password non si recuperano: sono hash argon2, si sostituiscono; minimo 12 caratteri, chieste in modo interattivo). Lo stesso username può esistere in ristoranti diversi.
- **Più ristoranti** (intent 0003, fase 3a fatta): ogni `Restaurant` ha `slug` (`app/slugs.py`: formato e parole riservate) e `active`; menu, tavoli e quindi sessioni, ordini e pagamenti appartengono a un ristorante. Ruoli: `SUPERADMIN` (admin centrale, `restaurant_id` nullo: gestisce ristoranti e utenti, **non** i loro dati → 403 sugli endpoint operativi), `ADMIN` e `WAITER` (di un ristorante). **Isolamento**: ogni endpoint staff filtra per `RestaurantId` (`app/deps.py`) e le risorse di un altro ristorante rispondono 404; per i path con `session_id` si usa `dependencies=[SessioneDelRistorante]`. Se aggiungi un endpoint staff devi filtrare e aggiungere il caso a `tests/test_tenancy.py` (che deve fallire se togli un filtro). Il ristorante dell'utente si legge sempre dal DB, mai dal token; utente o ristorante disattivati → 401 subito. Login: `POST /api/auth/login` con `restaurant` (slug) per lo staff, senza per l'admin centrale; **transitorio** (fino alla fase 3d) senza slug entra anche uno staff con username univoco. Menu: `GET /api/menu` e `/api/menu/all` sono dello staff e del suo ristorante; per i clienti `GET /api/public/restaurants/{slug}` e `/menu`. **Indirizzi e QR (3c)**: il QR codifica `FRONTEND_URL/ristorante/<slug>/tavolo/<id>?token=…` (`qr_url(table, slug)`; senza slug il vecchio `/table/<id>`, che resta valido); `PublicTableOut.restaurant_slug` dice a quale ristorante appartiene il tavolo e il frontend reindirizza sempre allo slug giusto (mai ai dati di un altro locale). `parseTableLink` accetta entrambe le forme. Rotte frontend: `/ristorante/:slug` (pagina pubblica, `restaurant/RestaurantHome`), `/ristorante/:slug/accesso` (login staff con slug), `/ristorante/:slug/admin|waiter/*`, `/ristorante/:slug/tavolo/:id`, `/piattaforma/*`, `/cambio-password`; `/admin`, `/waiter`, `/table/:id` sono vecchi indirizzi che portano al ristorante giusto (`useStaffBase` in `staff/paths.ts` dà il prefisso alle rotte dello staff). **Utenti del ristorante**: `/api/users` (solo ADMIN, stesse regole di `app/users.py`; non si agisce su sé stessi) e schermata `admin/UsersScreen`. **Password provvisoria**: chi crea o reimposta un utente imposta `must_change_password`; finché non cambia password gli endpoint con ruolo rispondono 403 (restano `/api/auth/me` e `POST /api/auth/change-password`, che chiede la password attuale e risponde con un token nuovo) e il frontend porta a `/cambio-password`; la sessione staff ricorda `restaurant` e `mustChangePassword` (se il server risponde 403 «Devi cambiare la password…» la sessione passa subito al cambio obbligatorio). **Revoca dei token staff**: cambiare o reimpostare la password (anche da CLI) imposta `app_user.password_changed_at` e `get_current_user` rifiuta i JWT con `iat` precedente (i token portano `iat`); chi cambia la propria password riceve un token nuovo; la colonna è nullable (migration compatibile). Nel pannello c'è il pulsante «Password» per cambiarla di propria volontà. **Admin centrale** (fase 3b): `/api/platform/restaurants[/{id}[/users[/{uid}]]]` (solo `SUPERADMIN`, `PlatformUser`): crea/modifica/attiva ristoranti (slug validato da `app/slugs.py`) e gestisce i loro utenti; la logica degli utenti sta in `app/users.py` (password provvisoria → `must_change_password`, mai l'ultimo admin attivo, niente eliminazione se ha inserito ordini) ed è condivisa con la fase 3c. Frontend: `src/platform/` (`PlatformApp` su `/piattaforma/*`, solo `SUPERADMIN`; dopo il login l'admin centrale va lì) e il componente riusabile `src/admin/UsersPanel.tsx` (+ `password.ts` per le password provvisorie).
- Il QR di un tavolo (`GET /api/tables/{id}/qr.svg`, solo ADMIN) codifica `FRONTEND_URL/table/<id>?token=<qr_token>`: `FRONTEND_URL` va impostato su Vercel con il dominio di produzione. Il `qr_token` non è mai nell'elenco tavoli.
- Una sola sessione `OPEN` per tavolo: lo garantisce un indice unico parziale nel DB (le richieste concorrenti perdenti ricevono 409).
- Account dei clienti (`app/routers/customer.py`, `/api/customer/...`): registrazione e login con email e password, profilo, storico dei pagamenti, eliminazione dell'account. Tabella `customer` **separata** da `app_user` (staff). I token hanno un tipo (`typ`: `staff` o `customer`): `get_current_user` rifiuta i token cliente e `get_current_customer` quelli staff; i token staff vecchi senza `typ` valgono come staff. Token cliente da 30 giorni. Pagare al tavolo **non richiede** un account: `POST /api/public/tables/{id}/payments` accetta un token cliente facoltativo (`OptionalCustomer`) e, se valido, lega il pagamento all'account (`payment.customer_id`); se manca o non è valido si paga come ospite, senza errori. Eliminando l'account (`DELETE /api/customer/me`, serve la password) il pagamento resta (serve al ristorante) con `customer_id` nullo **e con `customer_nickname` sostituito da "Cliente eliminato"**: il nome digitato al tavolo è di solito nome e cognome, quindi senza questo passo i pagamenti non sarebbero davvero anonimi. L'informativa (`PrivacyPage`) e la finestra di eliminazione (`ProfilePage`) devono dire lo stesso: se cambi uno, cambia anche gli altri. I pagamenti da ospite non sono collegati a nessun account e non vengono toccati. Email sempre in minuscolo; password 8-128 caratteri; la registrazione richiede `accept_privacy` e salva `privacy_accepted_at`. Rate limit su registrazione (per IP) e login (per IP e per email, solo i falliti). **Nessuna verifica dell'email alla registrazione** (scelta di prodotto); nessun login Google per ora. **Recupero password** (intent 0004): `POST /api/customer/auth/password-reset/request` risponde sempre 202 con lo stesso testo (nessuna enumerazione), conta ogni richiesta nei limiti per IP e per email (`RATE_LIMIT_RESET_*`) e, se l'email esiste, crea un `password_reset_token` (hash SHA-256 del token, 1 h, uso singolo; quelli scaduti da più di un giorno si cancellano a ogni richiesta) e spedisce il link `FRONTEND_URL/reset-password#token=…` (nel frammento, mai in query) con `app/email.py` (Resend via httpx; senza `RESEND_API_KEY` ed `EMAIL_FROM` l'email non parte e il testo (con il link) va nel log **solo in sviluppo** (`EMAIL_LOG_LINKS`, acceso se `VERCEL` non c'è), in produzione si scrive solo che Resend non è configurato; un errore di invio non fa cadere la richiesta); `…/password-reset/confirm` (stesso errore 400 per link sconosciuto, usato o scaduto; limite per IP sui falliti) prende il link con un UPDATE atomico (`used_at IS NULL AND expires_at > now`: due conferme insieme non passano entrambe), imposta la password, chiude tutti i link aperti del cliente e imposta `customer.password_changed_at`. Cambiare o recuperare la password revoca i token cliente emessi prima (`iat` < `password_changed_at`); `POST /api/customer/me/password` chiede la password attuale e dà un token nuovo. **Ristoranti visitati**: `GET /api/customer/restaurants` (ristoranti con pagamenti COMPLETED/CASH del cliente: visite, ultima visita, totale) e `GET /api/customer/payments?restaurant=<slug>`. Frontend: `/password-dimenticata`, `/reset-password` (legge e toglie il token dal frammento, `account/resetToken.ts`), sezione «Cambia password» nel profilo, «I tuoi ristoranti» in `AccountHome`, filtro per ristorante nello storico. L'informativa (`PrivacyPage`: Resend tra i fornitori, base giuridica, staff, regioni dei server da `privacyConfig.ts`) e la finestra di eliminazione devono dire lo stesso.
- Ordini (`/api/sessions/{id}/orders`): `unit_price` è il prezzo del menu congelato al momento dell'ordine; il totale è sempre la somma di `quantity × unit_price`, mai ricalcolato dal menu. Ordini modificabili solo a sessione `OPEN` e **finché non esiste alcun pagamento** (altrimenti 409); una voce già pagata non si rimuove.
- Il codice dei pagamenti è simulato finché non si decide l'integrazione reale (es. Stripe).
- Pagamenti: la logica sta in `app/payments.py` (non fa commit; blocca la sessione con `FOR UPDATE`), gli endpoint in `app/routers/payments.py`. Gli errori di dominio (`app/errors.py`: `NotFound`/`Conflict`/`Invalid`) diventano 404/409/422. ROMANA: quota = totale/coperti arrotondata per difetto, **l'ultimo che paga copre il resto**; OWN: voci con quantità parziale, residuo = ordinato − già pagato. Online → `COMPLETED`; cassa → `CASH` finché il cameriere non conferma. La sessione si chiude da sola quando tutto è coperto (ROMANA: pagamenti ≥ coperti; OWN: ogni voce pagata) o con `POST /api/sessions/{id}/close`.
- Gli endpoint di `payments.py` sono per lo staff. I clienti usano `/api/public/tables/{id}` (`app/routers/public.py`), che riusa `app/payments.py`: si accede col token del QR nell'header `X-Table-Token` (non nell'URL). Tavolo inesistente, token sbagliato o assente → sempre lo stesso 404.
- Rate limit (`app/ratelimit.py`, tabella `rate_limit_counter`): contatori su Postgres a finestra fissa, aggiornati con `INSERT … ON CONFLICT DO UPDATE … RETURNING` su connessione propria con commit immediato (un contatore in RAM non funziona su Vercel serverless); le righe scadute si cancellano in modo opportunistico. Si supera il limite → 429 `TooManyRequests` con `Retry-After`. Login: solo i tentativi **falliti**, per IP e per username (esaurito il limite, anche la password giusta aspetta). Pubblici: token errato per IP (esaurito → 429 prima di guardare il token), richieste valide per tavolo (polling compreso), scritture (modalità, pagamenti) per tavolo. Gli endpoint staff con JWT non sono limitati. Soglie e finestre sono `RATE_LIMIT_*` in `app/config.py` (`RATE_LIMIT_ENABLED=false` le spegne); i valori predefiniti e il loro calcolo sono nella PR #16. L'IP si legge da `x-real-ip`/`x-forwarded-for` (ultimo valore) solo se `trust_proxy_headers` è attivo (di default lo è solo con `VERCEL` impostato): fuori da Vercel gli header sarebbero falsificabili. Se il contatore dà errore (es. migration non applicata) la richiesta passa e si logga. Nei test i contatori sono committati: `conftest.py` li azzera a fine test e i test di concorrenza li includono nel `TRUNCATE`.
- `tests/test_concurrency.py` usa connessioni e dati veri (committati, poi `TRUNCATE`): non spostarlo sulla sessione di test e non usare quelle tabelle in altri test senza `db` isolato. Se togli il `FOR UPDATE` da `app/payments.py` quei test devono fallire.
- Branch Neon di anteprima: l'integrazione ne crea uno per ogni deploy di anteprima e il piano gratuito ne ammette pochi (a fine limite i deploy falliscono con `Branch limit reached`). Il workflow `neon-cleanup.yml` li elimina alla chiusura della PR e ogni lunedì (`scripts/neon_cleanup.py`, che non tocca mai default, protetti o ciò che non inizia per `preview/`). Richiede il secret `NEON_API_KEY`; provalo prima con "Run workflow" lasciando `apply` spento.

- Commit in stile Conventional Commits (`feat:`, `fix:`, `chore:`…).
